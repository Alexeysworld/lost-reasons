# Методология определения реальной причины проигрыша (Midmarket)

Цель: по проигранной сделке определить **реальную** причину проигрыша, не доверяя
полю `Deal - Причина проигрыша` (его консультанты заполняют формально), а
восстанавливая правду из комментариев и заметок в Pipedrive.

Документ описывает: (1) почему нельзя верить указанной причине, (2) таксономию
реальных причин, (3) приоритет источников данных, (4) правила классификации,
(5) формат результата (категория + детализация + обоснование).

---

## 1. Почему указанная причина (поле E) не равна реальной

На размеченном эталоне за апрель 2026 (92 сделки) указанная причина расходится с
реальной в большинстве случаев. Кросс-таблица «указано → реально»:

| Указано консультантом | Реально оказалось |
|---|---|
| «выбрали конкурента / текущий стек / сделают сами» (32 шт.) | конкурент 24, **дорого 3, не заинтересовал ЛВР 2, нецелевой 1, перестал отвечать 1, SS 1** |
| «не готовы интегрироваться» (24 шт.) | интеграция 11, **конкурент 4, дорого 2, ЛВР 1, нецелевой 1, отвечать 1, отложить 1, SS 1** |
| «не нашёл подходящей причины» (15 шт.) | ЛВР 4, дорого 2, отложить 2, рук-ль заблокировал 2, конкурент 1, интеграция 1, нецелевой 2 |
| «не могу получить ответ» (16 шт.) | перестали отвечать 16 |
| «SS, маленькая база» (8 шт.) | SS 8 |

Вывод: поле `Причина проигрыша` — только слабая подсказка. Категориям
«не могу получить ответ» и «SS» можно доверять почти всегда; «выбрали конкурента»,
«не готовы интегрироваться» и «не нашёл причины» нужно **перепроверять по комментариям**.

## 2. Таксономия реальных причин

Канонические категории (нормализованные — в эталоне встречаются опечатки
«Перстали», «Нецелевой контакт», «Конкуренты», их сводим к канону):

| Категория | Когда ставим | Обязательная детализация |
|---|---|---|
| **Конкурент** | клиент остаётся на текущем стеке, выбрал другого вендора, или решил делать сами/inhouse | **какой именно** конкурент/стек: «остались на X», «выбрали X», «решили делать сами (inhouse)» |
| **Не готовы интегрироваться** | блокирует не цена и не интерес, а интеграция/ресурс | подтип, см. §2.1 |
| **Клиенту дорого, хотя база норм** | база адекватная, но цена/бюджет — стоп-фактор (в т.ч. «порезали бюджеты», «оптимизируют расходы») | при наличии: с чем сравнивают по цене / насколько дорого |
| **Не заинтересовал ЛВР** | дошли до ЛПР/ЛВР, но не увидел ценности/окупаемости, «не продали» | чем именно не зацепили (не верит в окупаемость и т.п.) |
| **Нет ресурса маркетинга** | у клиента некому вести платформу / нет маркетолога на стороне клиента (само по себе, не из-за сложной интеграции) | роль/ситуация: нет маркетолога вообще, ушёл, не выделен ресурс |
| **Перестали отвечать** | клиент пропал после контакта | на каком шаге пропал (после 1-й встречи / оффера / тех. подготовки) |
| **SS** | self-service, т.к. **маленькая база** (сегмент не наш) | размер базы, если известен |
| **Попросили отложить** | клиент явно просит вернуться позже (реорг, не приоритет сейчас) | срок и причина паузы |
| **Руководитель заблокировал решение** | решение зарубил вышестоящий, не доходя до проработки | кто/почему заблокировал |
| **Нецелевой** | не наша ЦА (B2B без B2C, не тот контакт, не та индустрия) | чем нецелевой |

> Важно про «Нет ресурса маркетинга»: это **отдельная категория** (по решению заказчика
> от 15.06). В апрельском эталоне такие кейсы лежали внутри
> «Не готовы интегрироваться: Нет маркетолога…» — поэтому при сверке с апрельским
> эталоном они будут считаться расхождением (на деле — смена таксономии, а не ошибка).
> Отличать от «Не готовы интегрироваться»: если блокер — именно **интеграция/разработка**,
> а маркетолога нет дополнительно, остаётся интеграция; если интеграция в принципе ок,
> но **некому работать в платформе** — ставим «Нет ресурса маркетинга».

### 2.1 Подтипы «Не готовы интегрироваться»

| Подтип | Триггер | Детализация |
|---|---|---|
| Нет готового модуля интеграции | у клиента система, с которой у нас нет коннектора | **назвать систему**: Intickets, YClients, «Стартер», … |
| Сложная / кастомная интеграция | интеграция технически тяжёлая, высокий риск | с чем: МИС, BeautyExpert, … |
| Разработка в процессе | клиент сейчас обновляет сайт / делает приложение / переезжает на 1С/Битрикс | что именно делают |

(Подтип «нет маркетолога» вынесен в отдельную категорию **Нет ресурса маркетинга**, см. §2.)

## 3. Приоритет источников данных (что читать и в каком порядке)

Для каждой сделки собираем из Pipedrive (MCP) и взвешиваем в этом порядке:

1. **`Deal - Коммент при проигрыше Midmarket` (поле G)** — самый честный короткий
   сигнал. Часто прямо противоречит указанной причине («порезали бюджеты»,
   «нет интеграции с интикетс», «не продал», «дорого и перестала отвечать»).
2. **Свежие internal-заметки менеджера у даты проигрыша** (Notes, тип `comment`,
   часто 📌pinned) — например «руководство заворачивает проекты, бюджет сократили»,
   «закрывают точки, оптимизируют бюджет», «не верю в окупаемость».
3. **Заметка «Оценка встречи – …»** → блоки **«Прогноз по сделке»**, **«Что тормозит»**,
   **«Статус сделки»**. Структурированно перечисляет блокеры.
4. **Поле `Deal - Конкурент: что используют сейчас / какого конкурента выбрали?` (I)** —
   для имени конкурента/стека.
5. **Исходящие письма-резюме менеджера** (Notes) — иногда цитируют слова клиента
   («ваш тариф в 3 раза дороже текущего контракта»).
6. Транскрипции встреч — читать только если 1–5 не дали ответа (длинные, шумные).

Сигналы из 1–3 перевешивают указанную причину E. Если они противоречат друг другу —
берём **самый поздний по времени** (ближе к моменту проигрыша) и более конкретный.

`scripts/notes_digest.py` готовит из дампа Notes компактную выжимку именно этих
блоков (прячет lead-capture автозаметки и транскрипции).

## 4. Правила классификации (дерево решений)

Применять по порядку; первая сработавшая ветка побеждает.

1. **Имя конкретного конкурента/стека** в G/I/заметках, и причина ухода — остаться
   на нём / выбрать его / делать сами → **Конкурент** (детализация = имя).
   - НО: если конкурент назван, а реальный стоп — цена («в 3 раза дороже»,
     «дешевле у текущего») и клиент скорее остаётся по экономике → можно
     **Клиенту дорого** или **Конкурент** с пометкой про цену; смотри, что
     доминирует в последних заметках. (Эталон 338294: остаются на Премиум Бонус
     + просили отложить → «Конкурент: вероятно Премиум бонус, но попросили отложить».)
2. **Маленькая база / self-service** → **SS**.
3. **Цена/бюджет — главный стоп, база нормальная** («дорого», «порезали бюджеты»,
   «оптимизируют расходы», «не проходит по экономике») → **Клиенту дорого, хотя база норм**.
4. **Блокер — интеграция** (нет модуля / сложно / идёт разработка) →
   **Не готовы интегрироваться** + подтип (§2.1).
5. **Блокер — нет маркетолога / некому вести платформу** (интеграция при этом не
   главный стоп) → **Нет ресурса маркетинга**.
6. **Дошли до ЛПР, но не убедили** («не продал», «не верит в окупаемость») →
   **Не заинтересовал ЛВР**.
7. **Вышестоящий зарубил** → **Руководитель заблокировал решение**.
8. **Просят вернуться позже** (реорг, «сейчас не приоритет», конкретный срок) →
   **Попросили отложить**.
9. **Не наша ЦА / не тот контакт** → **Нецелевой**.
10. **Просто пропал, контента нет** → **Перестали отвечать** (+ на каком шаге).

Если данных нет вообще (только формальная причина и пустой коммент) — берём указанную
причину как есть и ставим `confidence: low`.

## 5. Формат результата

К входному xlsx добавляем 4 колонки (см. `scripts/xlsx_io.py`):

- **Реальная причина проигрыша (авто)** — канонная категория из §2.
- **Детализация (конкурент X / модуль Y)** — обязательна для «Конкурент»
  (кто) и «Не готовы интегрироваться» (какой модуль/подтип); для остальных —
  короткое уточнение, если есть.
- **Обоснование** — 1–3 предложения: какой источник (поле G / заметка от ДД.ММ /
  блок «Что тормозит») и какая дословная зацепка привели к выводу. Должно позволять
  проверяющему за 10 секунд понять логику без открытия сделки.
- **Уверенность** — high / medium / low.

Пример (сделка 367712, collegiummusicum):
- Реальная причина: `Не готовы интегрироваться`
- Детализация: `Нет готового модуля интеграции с билетной системой Intickets`
- Обоснование: `Коммент при проигрыше: «нет интеграции с интикетс». На встрече
  (заметка 07.04) клиент: «через что интегрируется с Intikits?»; конкурент ранее
  отказался писать интеграцию (~1.5 млн). Блок «Что тормозит»: тех. неопределённость
  по интеграции с Intikits — блокирующий фактор.`
- Уверенность: `high`
